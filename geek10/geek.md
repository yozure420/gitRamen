1. 構成の選択とその代償

なぜ SQLite なのか

- SQLite を選んだ理由は、履歴にも docs にも残っていません。 発表前に本人たちに聞いてください
- 推測で言えそうな理由：
  - DB サーバーが不要で、Docker のボリューム 1 つで運用できる
  - 学生チームのインフラ費用がゼロで済む
- 実際に払った代償（ここが話のネタになります）
  - 本番は gunicorn の4 ワーカーで動かしています。そのため、起動時のマイグレーションが 4 プロセス同時に走ります（→ 3-①）
  - キャッシュがワーカーごとに分かれ、外部 API のレート制限に引っかかりそうになりました（→ 3-④）
  - 「いずれ PostgreSQL にも移せるように」と、SQLite 専用の書き方（check_same_thread、PRAGMA）をあとから取り除きました（#60 / #69）

N+1 問題はあったか

- 見つかりませんでした。 正直に言うのが一番ウケます
- 理由：
  - マイページの統計（よくミスするコマンド Top 10）は、JOIN と GROUP BY を使ったクエリ 1中で毎回 DB を引く書き方をしていません
  - 外部キー（user_id、history_id、miss_command_id）にはすべてインデックスを付けています
  - レスポンスで、関連先のデータを後から読み込む（lazy load）ようなアクセスをしていません
- 言い方の例：「N+1 は、起きない書き方を最初からしていました。確認のためにコードを全部見直したところ、ありませんでした」

2. 🤯「そんなことある！？」集（本命）

① SQLite の ALTER TABLE は、トランザクションの中でも即座に確定する

- 症状：列を追加したあとのデータ更新が失敗しても、列の追加だけが残ってしまう
- 原因：Python の SQLite ドライバ（pysqlite）は、DDL（ALTER など）の前に BEGIN を出しません。そのため ALTER は、その場で確定してしまいます
- 解決：
  - 自動コミットを止め、自分で BEGIN IMMEDIATE と COMMIT を出すようにした
  - さらに、4 ワーカーが同時に起動して列の追加が競合した場合は、「失敗したあとに列が存在するか」を調べ直し、あれば無視するようにした
- 検証：古いスキーマの DB（20,000 行）に、4 プロセスから同時に 12 回マイグレーションをかけ、どれも失敗しないことを確かめました（#69）

② NOT IN で、NULL の行だけがすり抜ける

- 症状：「遊べないコマンドを playable=false にする」UPDATE で、command が NULL の行だけ
- 原因：SQL の三値論理です。NULL IN (...) は「偽」ではなく「不明（NULL）」になり、それを NOT しても NULL のままなので、WHERE で拾われません
- 解決：command IS NULL を条件に明示的に足した
- 言い方の例：「NULL は『偽』ではなく『分からない』です」

③ テストのモックを毎回リセットしていたら、未処理のエラーが出た

- 原因：Vitest は、beforeEach が関数を返すと、それを後片付けの処理として実行します。beforeEach(() => mock.mockReset()) と書くと、mockReset() がモック関数自身を返します。そのモックがテスト後に呼ばれて Promise
  が reject され、未処理のエラーになっていました
- 解決：アロー関数の {} を付けて、何も返さないようにした（cd822d3）
- 言い方の例：「{} を付けるかどうかで、テストが壊れるかどうかが決まりました」

④ E2E のモックが、ソースコードそのものを横取りした

- 症状：E2E テストでだけ、アプリが起動しない
- 原因：Playwright で API をモックする条件を **/api/news* と書いていました。開発サーバーでは /src/api/news.ts というソースファイルも配信されているので、このパターンに一致してしまいます。その結果、JavaScript のモジュールの代わりに JSON が返り、アプリが起動しませんでした
- 解決：パターンを正規表現 /\/api\/news(\?.*)?$/ に変えた

⑤ デプロイすると、開いたままのタブが真っ白になる

- 原因：画面ごとにコードを分割して配信しています。デプロイすると古いファイル（ハッシュ付きのチャンク）がサーバーから消えるので、開いたままのタブで画面を移ると読み込みに失敗します
- 解決：読み込みに失敗したら、一度だけページを再読み込みする（lazyWithReload）
  - 無限に再読み込みしないよう、sessionStorage に「再読み込み済み」の印を残す
  - さらに、sessionStorage が使えない環境（プライベートモードなど）では、印を残せず無限ループになり得るので、そもそも再読み込みしない
- 言い方の例：「無限ループを防ぐための仕組みが壊れたときの対策までしています」

⑥ 自分で出したタイマーが、他人のウィンドウを閉じる

- 症状：git status を打ってからイベントが起きると、そのイベントの告知が 3 秒で勝手に消える
- 原因：setTimeout(() => setStatusWindow(null)) が、その時点で何が表示されているかを確かめずに閉じていた
- 解決：setStatusWindow(current => current === snapshot ? null : current)
  - 自分が出したオブジェクトと同じ参照のときだけ閉じる
  - オブジェクトの参照そのものを「誰が出したか」の目印に使うので、ID を振る必要がありません（#68）

⑦ Git の手順どおりに遊ぶと、必ず失敗になる

- 症状：来客の注文を、git branch → git checkout で新しいレーンに移って push すると、毎回「誤配達」と判定される
- 原因：配達先が「注文を受けた時点のレーン」に固定されていた
- 解決：配達先を、新しく開くレーンにした
- 言い方の例：「Git を教えるゲームで、Git の手順どおりにやると負ける。最初は気づきません

⑧ 本番が、リポジトリに載っている鍵で JWT を署名していた（可能性が高い）

- 原因：
  a. .dockerignore で .env を除外している → イメージに .env が入らない
  b. 本番の compose は環境変数で鍵を渡していない
  c. その結果、コードに書かれた既定値 dev-secret-key-change-in-production が使われる
- 解決：既定値をなくし、公開済みの鍵や短い鍵では起動しないようにした（#75）
- おまけ：compose で ${VAR:?} を使って鍵を必須にしたら、docker compose down まで止まるよ いないと、止めることすらできません

⑨ bcrypt は 72 バイトより後ろを黙って捨てる

- パスワードの上限が 100 文字なら、全角で最大 300 バイトになります。そのうち 73 バイト目以降は、照合に使われていませんでした
- さらに、ログインには長さの上限がなく、4096 バイトを超えると passlib が例外を出して 500います）
- 時限爆弾：bcrypt を 4.1 以降に上げると、72 バイトを超える入力でエラーになります。以前の上限で長いパスワードを登録した人がログインできなくなるので、バージョンを固定している理由をコメントに残しました

④ キャッシュ設計の進化（設計の話をするならここ）

1. 最初：取得結果を丸ごと 60 秒キャッシュしていた
   - → 4 つの取得元のうち 1 つが障害を起こしている間、正常な GitHub API まで毎分呼び直し、レート制限を使い切ってしまう
2. 改善：
   - 取得元ごとにキャッシュする
   - 失敗した結果も短い時間だけキャッシュする（ネガティブキャッシュ）
   - キャッシュが切れた瞬間にアクセスが集中しても、asyncio.Lock で外部への取得を 1 回にまとめる（thundering herd 対策）
3. 残っている課題（#66）：
   - キャッシュとロックが gunicorn のワーカーごとに分かれている
   - 試算（未計測）では、GitHub API の呼び出しが1 時間あたり約 48 回で、認証なしの上限（1 時間あたり 60 回）に近い
- 言い方の例：「プロセスの中のキャッシュは、ワーカーの数だけ分かれてしまいます」
